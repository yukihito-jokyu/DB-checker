# skill-feedback-loop

ユーザーの指摘を現在の成果物の修正と、将来のAI作業を改善する仕組みの両方へつなげる。skill改善を先行させず、指摘の理解、議論、合意した修正、検証を先に完了する。

## 記録

開始時に [record-format.md](references/record-format.md) を読む。

- 保存先は `.local/skill-feedback/<YYYYMMDD-HHMMSS>-<slug>/feedback.md` とする。
- `.local/` がGitでignoreされていることを確認してから保存する。ignoreされていなければ、記録前に `.gitignore` の更新方針をユーザーへ示す。
- 起点となる指摘ごとに新しいディレクトリを作る。同じ問題を掘り下げる応答は同じ記録へ追記し、独立した指摘は分ける。
- 起点のユーザー指摘は原文で残す。ただし秘密情報、認証情報、個人情報は伏せる。
- 議論では、ユーザーと合意した内容、採用・却下した案、その理由、未決事項を残す。AIの非公開な思考過程は記録しない。
- 状態が変わるたびに現在状態と更新日時を更新する。

## ワークフロー

### 1. 指摘を受け付ける

1. 指摘を `discussing` として直ちに記録する。
2. 対象成果物、期待との差、影響範囲を整理する。
3. 不明点が結果を左右する場合だけ、現在の問題についてユーザーへ確認する。
4. この段階ではskill、`AGENTS.md`、ルール類を変更しない。

記録作業のために議論や現在の修正を止めない。ユーザーへの応答は、まず指摘そのものに答える。

### 2. 現在の問題を解決する

1. 指摘への見解、選択肢、影響をユーザーと議論する。
2. 合意した修正内容と完了条件を記録する。
3. 現在の依頼で許可された範囲だけ成果物を修正する。
4. 修正をテスト、レビュー、またはユーザー確認で検証する。
5. 合意どおりの修正と検証が済んだ場合だけ `artifact-resolved` にする。

修正未完了、未検証、または議論中なら、skill改善候補の調査へ進まない。

### 3. 改善先を調査する

`artifact-resolved` 後に、プロジェクト内の `AGENTS.md` と `.agents/skills/` を調査する。起点の作業で使用したskill、その責務に近いskill、関連referenceを優先する。

次を満たす指摘だけ、仕組みの更新候補にする。

- 今後の同種作業にも適用できる。
- 既存指示の欠落、曖昧さ、競合、または実行手順の不足が原因である。
- 更新により同種の失敗を具体的に防止または検出できる。

単発の好み、対象成果物だけの問題、既存指示を守らなかっただけの問題は、安易にskillへ追加しない。既存指示の強調、検証手順の追加、テンプレートやスクリプト化のどれが再発防止に有効かを比較する。

更新先は次の優先順で決める。

1. 判断を所有する最も狭い既存skillまたはreference。
2. 複数skillに共通するプロジェクト規約なら `AGENTS.md`。
3. 決定的な反復処理ならskill内のtemplateまたはscript。
4. どこにも自然に属さず、独立した反復ワークフローなら新規skill。
5. 仕組みの更新が不要なら `closed-no-change`。

同じ規則を複数箇所へ重複させない。候補を比較し、採用先と不採用先の理由を記録する。

### 4. 更新計画を提示する

変更前に `skill-change-proposed` とし、ユーザーへ次を提示する。

- 一般化した教訓。
- 更新が必要な理由と、更新しない場合の再発リスク。
- 推奨する更新先と、その責務に適合する理由。
- 変更するファイルと具体的な修正内容。
- 変更しない範囲と、過剰適合を避ける考え方。
- 検証方法。
- 代替候補があれば、採用しない理由。

ローカルファイルは絶対パスのクリック可能なMarkdownリンクで示す。明示的な承認を求め、承認前はskill、reference、template、script、`AGENTS.md` を変更しない。

### 5. 承認結果を反映する

- 承認: 対象ごとの承認範囲を記録し、その範囲だけ更新する。skillの作成・更新では `skill-creator` を使い、`quick_validate.py` と参照整合性を検証する。
- 修正付き承認: 計画と記録を更新してから、修正後の範囲だけ反映する。
- 見送り: 理由を記録し `deferred` または `closed-no-change` にする。仕組みは変更しない。

反映後は差分と検証結果を記録し、`applied` にする。新たな一般化判断が必要になった場合は、承認範囲を広げずユーザーへ戻す。

## 完了条件

- 起点指摘、議論の決定事項、成果物の修正、検証結果がローカル記録にある。
- 成果物の問題がskill改善より先に解決されている。
- 仕組みを変える場合は、更新理由、更新方法、対象、検証方法が承認されている。
- 承認範囲だけが変更され、検証結果と最終状態が記録されている。
