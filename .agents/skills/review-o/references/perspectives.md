# Perspectives

4視点を別々のサブエージェントへ固定分担する。各担当は同じ入力マニフェストから開始し、他担当の結論を見ない。

## 共通依頼

各担当へ以下を伝える。

- 読み取り専用。編集、format、generate、Issue・PR投稿は禁止。
- 問題発見を成功条件にせず、指摘なしを許容する。
- findings first、重大度順で返す。
- 対象ファイルを `確認済み / 未確認 / 対象外` に分ける。
- 指摘ゼロでも、確認した主要事項、未確認範囲、テストギャップ、残リスクを返す。
- 視点外の重大問題は `越境候補` と明示し、通常候補と混ぜない。

各候補は次の形式にする。

| 項目 | 内容 |
| --- | --- |
| 候補ID | 視点接頭辞と連番。`DOC-01`、`ARC-01`、`READ-01`、`ADV-01`。 |
| 提案重大度 | blocker / high / medium / low。 |
| 主張 | 1件の具体的な問題。 |
| 仕様・規約根拠 | Issueの条件、文書の節、規約の該当箇所。 |
| 実装根拠 | working treeレビューはクリック可能な絶対パスと行番号。過去commitはcommit permalinkまたは `SHA:path:line`。 |
| 影響 | 失敗、保守リスク、ユーザー影響。 |
| 反例・誤検知条件 | 指摘が成立しない条件。 |
| 確信度 | high / medium / lowと理由。 |

最後に候補総数、確認済みファイル、未確認ファイル、問題なしと確認した事項、残リスクを付ける。

## DOC: 文書ロジック

Issueと承認済み文書にある事前条件、分岐、状態遷移、エラー、境界値、不変条件、受け入れ条件を実装とテストへ対応づける。文書にない望ましい仕様を追加しない。資料の欠落や矛盾は実装不備と分ける。

## ARC: プロジェクト規約・責務

適用される `AGENTS.md` と専門skillを読み、配置、依存方向、層境界、DTO、interface、ログ、コメント、テスト責務、既存契約との適合を確認する。新skillへ専門規約を複製せず、正本を根拠にする。

## READ: 可読性

命名、制御フロー、抽象化、重複、局所理解、テストの意図表現を確認する。個人の好みだけの指摘は禁止し、誤修正、バグ混入、仕様理解の阻害につながる具体的な影響を示す。

## ADV: 懐疑的・敵対的検証

攻撃的な文体ではなく、正常性の主張を反例で崩す。境界値、失敗順序、部分更新、競合、キャンセル、再試行、機密漏えい、偽陽性テスト、暗黙前提、未追跡・生成物の漏れを確認する。仮説ごとに具体的な入力、状態遷移、失敗結果、根拠を要求し、無制限に懸念を列挙しない。

## 実行上の独立性

- 4視点を1担当へ兼務させない。
- 実行枠が3以下なら `3 + 1` など複数波で実行する。
- 後続担当へ先行担当の出力を渡さない。
- 共有ファイルへ中間結果を書かせない。
- 実装担当者をレビュー担当へ再利用しない。
