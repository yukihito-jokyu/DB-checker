# Adjudication

メインエージェントが全候補を判定する。サブエージェントの票数や断定は判定根拠にしない。

## 判定台帳

全候補IDについて次を保持する。

- 視点と候補ID
- 提案重大度、主張、根拠、影響、確信度
- 判定: `採用` または `未採用`
- メインが決めた重大度
- 採用理由または未採用理由
- 正規化した採用ID
- 重複・統合先ID

採用は有効な指摘、文書矛盾、または明示すべき残リスクとして認めることを指し、修正許可を意味しない。

## 判定手順

1. 全担当の候補総数と受領した元候補IDを照合する。
2. 各候補の仕様・規約根拠と実装根拠をメインが直接開く。
3. 対象範囲、事実関係、影響、反例・誤検知条件を確認する。
4. 同じ原因の候補を正規化する。最も根拠が強い候補を採用し、他の元候補は統合先を示して未採用にする。
5. 矛盾する候補は両方の根拠を検証し、それぞれ判定する。
6. 採用した正規化済み指摘へ `S-01` 形式のIDと重大度を付ける。
7. 全元候補が一度だけ採用または未採用へ対応していることを監査する。

## 採用基準

- レビュー対象内である。
- 引用したIssue、文書、規約、コードが実在し、主張を直接支える。
- 実装の失敗経路、要件不一致、責務違反、または具体的な理解・保守リスクを説明できる。
- 反例を考慮しても問題が成立する。

テスト成功だけで候補を未採用にしない。静的な規約違反や可読性問題に、実行可能な再現テストを必須としない。

## 未採用理由

定型語だけで終えず、反証または境界を具体的に書く。

- 重複: 統合先IDと同一原因である理由。
- 根拠不足: 確認できない資料、行、因果関係。
- 事実誤認: 実際の制御・データフローなどの反証。
- 対象外: 今回固定した変更集合との境界。
- 好みのみ: 具体的な理解・保守リスクがない理由。
- 解消済み: 対応箇所と成立しなくなった経路。
- 意図された仕様: 承認済み根拠。
- 再現不能: 検証した入力・状態と結果。
- 判断材料不足: 不足資料と解消条件。未解決事項としても報告する。

根拠リンクが存在しない、または別内容を指す候補は採用しない。メインが新しい指摘を発見した場合は `MAIN-01` 形式で台帳へ追加し、同じ基準で判定する。
