# Adjudication

メインエージェントが全候補を判定する。サブエージェントの票数や断定を判定根拠にしない。

## 判定台帳

全候補IDについて次を保持する。

- 視点と候補ID
- 提案重大度、主張、根拠、再現条件、影響、確信度
- 判定: `採用` または `未採用`
- メインが決めた重大度
- 採用理由または未採用理由
- 正規化した採用ID
- 重複・統合先ID

採用は有効な指摘、文書矛盾、または明示すべき残リスクとして認めることを指し、修正許可を意味しない。

## 判定手順

1. 全担当の候補総数と受領した元候補IDを照合する。
2. 各候補の仕様・規約・実装根拠をメインが直接開く。
3. 対象範囲、事実関係、再現条件、影響、反例を確認する。
4. 実行可能で安全な場合は、型検査、build、テスト、生成CSS、実DOMなど候補に合う方法で反証を試みる。
5. 同じ原因の候補を正規化する。最も根拠が強い候補を採用し、他は統合先を示して未採用にする。
6. 採用した正規化済み指摘へ`S-01`形式のIDと重大度を付ける。
7. 全元候補が一度だけ採用または未採用へ対応していることを監査する。

## 重大度

- blocker: build不能、起動不能、主要データ破壊、秘密漏えいなどリリースを止める問題。
- high: 主要操作が完了しない、誤った対象を更新する、キーボード利用者が主要操作できないなど重大なユーザー影響。
- medium: 特定状態・viewport・失敗経路で操作や表示が破綻する、責務違反が具体的な不具合を誘発する問題。
- low: 現在の挙動を壊さないが、規約逸脱や局所理解の阻害による具体的な保守リスク。

頻度だけで重大度を下げず、影響と回避可能性を併記する。

## 採用基準

- 固定したレビュー対象内である。
- 引用したIssue、文書、規約、コードが実在し、主張を直接支える。
- 失敗経路、要件不一致、責務違反、アクセシビリティ失敗、または具体的な保守リスクを説明できる。
- 反例を考慮しても成立する。

テスト成功だけで候補を未採用にしない。静的規約違反へ再現テストを必須としない。画面未確認だけを根拠に表示不具合と断定しない。

## 未採用理由

定型語だけで終えず、反証または境界を具体的に書く。

- 重複: 統合先IDと同一原因である理由。
- 根拠不足: 確認できない資料、DOM、class適用、因果関係。
- 事実誤認: 実際のprops、状態遷移、CSS生成、Wails契約などの反証。
- 対象外: 固定した変更集合またはfrontend境界との関係。
- 好みのみ: 具体的なユーザー影響・保守リスクがない理由。
- 解消済み: 対応箇所と成立しなくなった経路。
- 意図された仕様: 承認済み根拠。
- 再現不能: 検証したviewport、入力、状態、操作と結果。
- 判断材料不足: 不足資料と解消条件。

根拠リンクが存在しない、または別内容を指す候補は採用しない。メインが新しい指摘を発見した場合は`MAIN-01`形式で台帳へ追加し、同じ基準で判定する。
