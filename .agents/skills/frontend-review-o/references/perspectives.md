# Perspectives

4視点を別々のサブエージェントへ固定分担する。各担当は同じ入力マニフェストから開始し、他担当の結論を見ない。

## 共通依頼

各担当へ次を伝える。

- 読み取り専用。編集、format、generate、Issue・PR投稿は禁止。
- 問題発見を成功条件にせず、指摘なしを許容する。
- findings first、重大度順で返す。
- 対象ファイルを `確認済み / 未確認 / 対象外` に分ける。
- 指摘ゼロでも、確認した主要事項、未確認範囲、テストギャップ、残リスクを返す。
- 視点外の重大問題は `越境候補` と明示し、通常候補と混ぜない。

各候補は次の形式にする。

| 項目 | 内容 |
| --- | --- |
| 候補ID | 視点接頭辞と連番。`REQ-01`、`ARCH-01`、`UI-01`、`RUN-01`。 |
| 提案重大度 | blocker / high / medium / low。 |
| 主張 | 1件の具体的な問題。 |
| 仕様・規約根拠 | Issueの条件、承認済み文書、適用規約。 |
| 実装根拠 | working treeは絶対パスと行番号。過去commitはcommit permalinkまたは`SHA:path:line`。 |
| 再現条件 | viewport、入力、データ状態、操作順序など。静的問題は成立条件。 |
| 影響 | ユーザー影響、失敗、保守リスク。 |
| 反例・誤検知条件 | 指摘が成立しない条件。 |
| 確信度 | high / medium / lowと理由。 |

最後に候補総数、確認済み・未確認ファイル、問題なしと確認した事項、残リスクを付ける。

## REQ: 要件・UI状態

Issueと承認済み文書にあるユーザー操作、表示内容、事前条件、分岐、状態遷移、エラー、境界値、受け入れ条件を実装とテストへ対応づける。

特に次を確認する。

- 初期、読み込み中、成功、空、エラー、再試行、操作中、部分失敗のうち必要な状態。
- 表示条件、操作可否、戻る・キャンセル、成功後・失敗後の状態。
- 長文、空文字、最大件数、狭いviewportなど仕様に関係する境界。
- 文言、状態表示、フィードバックが要件と一致するか。

文書にない望ましい仕様を追加しない。資料の欠落や矛盾は実装不備と分ける。

## ARCH: React・Wails責務

`AGENTS.md`と`frontend-implementation`を正本として、配置、依存方向、props境界、状態所有、データ変換、型、生成物境界を確認する。

特に次を確認する。

- `main`、router、page、feature、component、hook、service、libの責務。
- pageへの表示ロジック集中、過剰抽象化、重複した状態、派生状態の同期ずれ。
- Wails binding importがserviceへ閉じているか、runtime APIがadapterへ閉じているか。
- 生成型と画面型の変換位置、nullable/optional、エラー契約の扱い。
- コンポーネントAPI、命名、import、Props型、ref方針が既存規約と整合するか。

Go backend内部は判定対象にせず、frontend契約を判断するため必要な範囲だけ読む。

## UI: UI実装・アクセシビリティ

`shadcn`、Tailwind設定、既存`components/ui`を正本として、実DOM、操作性、視覚状態、実装記法を確認する。

特に次を確認する。

- semantic token、variant、`cn`、`gap`、`size-*`、class順序、raw color、重複・競合class。
- shadcn/Radixのcomposition、Dialog title、AlertDialog action、Select group、Fieldのinvalid/disabled表現。
- ラベル、accessible name、role、aria関係、キーボード操作、フォーカス開始・復帰、Escape、outside click。
- disabled、loading、errorの見た目とネイティブ属性・data属性・操作抑止の一致。
- 狭幅、長文、ズーム、overflow、折り返し、タップ領域、コントラスト、light/darkテーマ。
- Tailwindのバージョンと生成CSSでclassが有効か。

好みだけの指摘は禁止し、誤操作、理解阻害、表示崩れ、アクセシビリティ失敗、記法逸脱の具体的な影響を示す。

## RUN: 実行時・敵対的検証

正常性の主張を具体的な反例で検証する。攻撃的な文体や無制限な懸念列挙は避ける。

特に次を確認する。

- 二重送信、連打、遅延応答、順序逆転、stale response、unmount後処理。
- 保存・削除・切替中の閉じる操作、再試行、キャンセル、フォーカス復帰。
- Wailsエラー、欠損データ、予期しないenum、通信不能、部分更新。
- 秘密値の表示、ログ、toast、DOM残留。
- 大量項目、重い再描画、無限effect、不要な再取得。
- テストが失敗経路を実証するか、mockが実契約と乖離していないか、偽陽性にならないか。
- build、型検査、lint、E2Eが対象要件をどこまで保証するか。

仮説ごとに入力、状態遷移、期待結果、実際の失敗結果、根拠を要求する。

## 実行上の独立性

- 4視点を1担当へ兼務させない。
- 同時実行枠が3以下なら`3 + 1`など複数波で実行する。
- 後続担当へ先行担当の出力を渡さない。
- 共有ファイルへ中間結果を書かせない。
- 実装担当者をレビュー担当へ再利用しない。
